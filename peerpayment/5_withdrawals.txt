Withdrawals
A PeerPay withdrawal is a merchant-created payout request. Your backend locks the amount, the customer confirms the destination account on hosted checkout, then one of your agents sends the money from a receiving account they already hold. PeerPay verifies the transaction and tells you the result.

PeerPay does not hold funds or execute the bank transfer. Your API integration is create, redirect, then wait for a signed webhook or poll. Requires withdrawals:create / withdrawals:read.

Before you call the API
These are fulfillment prerequisites. The create call may still return a created withdrawal before the workspace is ready, but PeerPay cannot route it automatically until an eligible agent and account exist:

Add at least one approved receiving account in Workspace (https://peerpayment.org/dashboard/workspace). This is the account your agent will send from.
Invite a withdrawal agent from the same Workspace page (https://peerpayment.org/dashboard/workspace). The agent signs in, accepts the invite, then waits for you to attach a receiving account.
Attach each accepted agent to one active, approved receiving account. Automatic routing only considers attached agents.
Give those accounts withdrawal float. Succeeded deposits increase spendable capacity; succeeded withdrawals and recorded drains reduce it. An agent with too little remaining float is skipped.
Create an API key with withdrawal scopes and register a webhook URL in Developer Controls (https://peerpayment.org/dashboard/developers).
Dashboard home: https://peerpayment.org. Open live requests later at Withdrawals (https://peerpayment.org/dashboard/withdrawals).

How a withdrawal moves
Your backend creates the request with a locked amount and receives checkout_url.
You redirect the customer to that URL. They must confirm the destination account themselves. Creating the request is not enough.
After confirmation, PeerPay picks an eligible attached agent automatically, or leaves the request in review for you to assign manually.
The selected agent copies the customer-confirmed account and amount, sends the transfer from their attached receiving account, then pastes the transaction ID on the withdrawal.
PeerPay verifies that transaction. When it matches, you get withdrawal.succeeded. Eligible pre-transfer orders get withdrawal.expired at the deadline. Active verification can finish after the deadline and emits withdrawal.failed if its result is negative.

2. Send the customer to checkout
Redirect the customer to the checkout_url PeerPay returned. That page is where they confirm which account should receive the money. Do not skip this step, even if you already sent a destination in the create call.

The amount is locked. Checkout cannot change it.
The customer must submit a bank and account number. Prefill is only a starting value.
The hosted page submits confirmation to POST /checkout-api/w/{token}/confirm:
Checkout confirm body
{
  "destination": {
    "bank": "telebirr",
    "account_number": "0933445566"
  }
}
Until that confirm succeeds, the withdrawal stays created and no agent is assigned. If the customer never opens or never confirms the page before expiry, the request becomes expired.

3. Agent assignment
Confirmation is the trigger. PeerPay then chooses between agents that already exist in your workspace.

Automatic: PeerPay selects an active agent attached to an approved receiving account with enough spendable float, preferring the agent who has waited longest.
Review / manual: If no agent qualifies, routing is manual-only, or the policy is disabled, the request becomes review_required. Assign an agent from Withdrawals.
There is no public API parameter for choosing an agent. Manual assignment is an operator action on the existing request; do not create a second withdrawal or ask the customer to confirm again.
Deposits into those receiving accounts are what create float. If agents have no recent succeeded deposits and you have not recorded capacity, automatic assignment will keep landing in review.
You can reassign only before the agent submits a transaction reference.
4. Agent sends and verifies
The assigned agent works from the withdrawal detail page. They copy the customer-confirmed destination and locked amount, send that transfer from the attached receiving account, then paste the transaction ID into the withdrawal verification form. This is a dashboard/agent action, not a second public /v1/withdrawals request.

PeerPay checks that the transaction is unused, matches the exact amount, happened after customer confirmation, and landed on the confirmed destination.
A good match becomes succeeded and emits withdrawal.succeeded.
A mismatch, duplicate, or provider problem usually becomes review_required (or remains retryable while verification is pending) so the agent can correct and resubmit the reference.
5. Listen for the outcome
Prefer signed webhooks. Poll GET /v1/withdrawals/:id only as a reconciliation fallback. Webhook delivery is at least once and may arrive out of order, so deduplicate by PeerPay-Event-Id and store the greatest sequence processed for each withdrawal.

Use a reversible wallet hold when you create the request. Then apply exactly one of these actions:

withdrawal.succeeded — verified and complete. Capture the existing hold exactly once, keyed by data.object.id.
withdrawal.expired — the eligible pre-transfer request reached its deadline. Release the hold exactly once.
withdrawal.failed — unsuccessful terminal outcome after the deadline. Release the hold exactly once.
withdrawal.cancelled — a workspace administrator cancelled before transfer submission. Release the hold exactly once. The normal verification path uses review_required for bad or ambiguous references, so treat that event as an operator queue, not as a successful payout.
withdrawal.verification_failed — the latest verification attempt was negative or could not be completed. It is non-terminal before the deadline; use decision_code and keep the wallet hold unchanged while evidence is corrected.
withdrawal.review_required — not finished. Someone in your workspace still has to assign an agent or correct the transfer evidence.

A configured withdrawal return_url must match an active workspace return domain. After destination confirmation, checkout returns with peerpay_withdrawal_id, merchant_withdrawal_id, and checkout_status=customer_confirmed. These values are informational; use signed webhooks for transfer outcomes.

The API field notification_status reports delivery of the latest withdrawal event: pending, delivered, retrying, exhausted, or disabled. It does not mean your application has processed the wallet change.

See the full envelope and signature rules in Webhooks.

Recommended Wallet Flow
When POST /v1/withdrawals succeeds, create one reversible hold for the exact amount. Key it by the PeerPay withdrawal id, not by a browser session.
Keep the hold unchanged for every non-terminal event, including withdrawal.verification_failed, withdrawal.review_required, and withdrawal.review_resolved.
Capture the hold only for a signature-verified withdrawal.succeeded event or an authenticated read that returns status=succeeded.
Release the hold only for a signature-verified withdrawal.failed, withdrawal.expired, or withdrawal.cancelled event, or the matching authenticated terminal status.
Make hold creation, capture, and release idempotent by withdrawal ID. Make webhook ingestion idempotent by event ID. These are separate guards and you need both.

Copyable Webhook Handler
Verify the signature against the raw body, enqueue the event once, and return 2xx within 10 seconds. Perform wallet changes in a worker transaction.

Webhook receiver
// Keep the raw request body. Parsing it before verification breaks the HMAC.
export async function receivePeerPayWebhook(request) {
  const rawBody = await request.text();
  const eventId = request.headers.get("PeerPay-Event-Id") ?? "";
  const timestamp = request.headers.get("PeerPay-Timestamp") ?? "";
  const signatureHeader = request.headers.get("PeerPay-Signature") ?? "";

  if (!verifyPeerPaySignature({
    secret: process.env.PEERPAY_WEBHOOK_SECRET,
    eventId,
    timestamp,
    rawBody,
    signatureHeader,
  })) {
    return new Response("Invalid signature", { status: 401 });
  }

  // Enqueue once by eventId, then acknowledge quickly. The queue worker below
  // performs wallet changes outside the webhook request.
  await enqueueWebhookOnce({ eventId, rawBody });
  return new Response(null, { status: 204 });
}
Withdrawal event worker
const releaseEvents = new Set([
  "withdrawal.failed",
  "withdrawal.expired",
  "withdrawal.cancelled",
]);

export async function processPeerPayWithdrawalEvent(event) {
  const withdrawal = event.data.object;

  await db.transaction(async (tx) => {
    // Insert has a unique constraint on event.id. A duplicate delivery exits.
    const inserted = await recordWebhookEventOnce(tx, event.id);
    if (!inserted) return;

    if (event.type === "withdrawal.succeeded") {
      await captureWithdrawalHoldOnce(tx, withdrawal.id);
      return;
    }

    if (releaseEvents.has(event.type)) {
      await releaseWithdrawalHoldOnce(tx, withdrawal.id);
      return;
    }

    // created, assigned, verification_pending, verification_failed,
    // review_required, and review_resolved never move customer funds.
    await updateWithdrawalProgress(tx, withdrawal.id, {
      status: withdrawal.status,
      verificationStatus: withdrawal.verification_status,
      decisionCode: withdrawal.verification?.decision_code ?? null,
      sequence: event.sequence,
    });
  });
}
The persistence helper names are illustrative. Back them with unique constraints on webhook event ID and withdrawal hold ID in your own database.

Status map
Status	What it means
created	Your backend created the request. Redirect the customer to checkout_url before anything else happens.
customer_confirmed	The customer confirmed the destination account on hosted checkout. PeerPay now tries to assign an agent.
assigned	An eligible agent received the request and can copy the destination, send the transfer, then submit the transaction ID.
review_required	No eligible agent was available, routing is manual, or verification needs a merchant/agent decision. Assign or correct from the dashboard.
transfer_submitted	The assigned agent submitted a transaction reference. Verification has started or can be retried.
verification_pending	PeerPay is checking the submitted transaction ID or reference against the bank or wallet APIs.
succeeded	The transfer matched the confirmed destination and locked amount. Capture the existing wallet hold once by PeerPay withdrawal ID.
expired	An eligible pre-transfer request reached the 60-minute deadline. Release the existing wallet hold once.
failed	A negative or exhausted verification became terminal at or after the deadline. Release the existing wallet hold once.
cancelled	A workspace administrator cancelled the request before transfer submission. Release the existing wallet hold once.

Event	What you should do
withdrawal.created	Create one reversible wallet hold keyed by data.object.id, then wait for customer confirmation.
withdrawal.customer_confirmed	Destination locked. PeerPay will assign an agent or mark the request for review.
withdrawal.assigned	An agent now owns the transfer. Automatic or manual assignment both emit this event.
withdrawal.review_required	Needs a dashboard action: assign an agent, or correct a rejected transaction reference.
withdrawal.transfer_submitted	The agent submitted a transaction ID. Wait for verification.

withdrawal.expired	Release the existing wallet hold exactly once; the withdrawal did not complete.
withdrawal.failed	Release the existing wallet hold exactly once; this outcome is terminal.
withdrawal.cancelled	Release the existing wallet hold exactly once; this outcome is terminal.
withdrawal.review_resolved	A review case was resolved. Recheck the current status before acting.
Edge cases that confuse first integrations
Create does not assign an agent. Assignment starts only after checkout confirmation.
Prefill is not confirmation. A destination in POST /v1/withdrawals is a hint. The customer still has to confirm.
No eligible agent becomes review, not failure. Check attachments, account approval, and spendable float, then assign manually.
Return URL is browser navigation only. Do not treat the customer coming back as proof the withdrawal succeeded.
Expiry is state-aware. Eligible pre-transfer orders expire after 1 hour. Active verification is allowed to finish; a negative result at or after the deadline becomes failed.
Do not capture on created or assigned. Keep the hold until withdrawal.succeeded, or poll until status is succeeded.
